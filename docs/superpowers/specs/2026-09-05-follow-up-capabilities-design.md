# 后续能力实现设计

## 目标

在现有角色鉴权、预约状态机和可信分诊闭环之上，补齐候补、就诊摘要、知识库治理、审计追踪与基础交付能力，使项目具备可演示、可验证的后端/全栈业务闭环。

## 范围

本阶段实现以下能力：

1. 候补队列：满号时加入候补，按风险优先级与创建时间选择候补，生成限时 offer，接受后原子创建预约。
2. 就诊摘要：医生完成预约时填写摘要和随访建议，患者只能查看自己的已完成摘要。
3. 知识库治理：管理员上传文本/Markdown 文档，按 SHA-256 去重，支持草稿、发布、回滚和版本查询；历史分诊证据不被覆盖。
4. 审计与追踪：为写操作生成 Trace ID，记录操作者、角色、动作、资源和结果，不记录密码、JWT、API Key 或完整主诉。
5. 检索评估：保留当前向量检索语义，增加离线评估命令和可审计的评估样例格式，不虚构指标。
6. 交付工程：提供 Docker Compose、本地部署说明和 GitHub Actions 的编译/测试流水线。

## 设计决策

- MySQL 仍是预约库存与状态的唯一事实来源；候补 offer 和预约创建在同一事务内完成。
- 候补优先级使用 `EMERGENCY=0`、`ROUTINE=10`、`UNKNOWN=20`，同优先级按 `created_at`、`id` 升序。
- offer 默认 15 分钟有效；过期后可由管理员/定时任务调用回收接口继续分发，不在本阶段引入消息队列。
- 就诊摘要不包含处方、诊断结论或敏感证件信息；医生只能操作自己排班下的预约。
- 知识文档只接受 UTF-8 文本和 Markdown，文件大小限制 2 MiB；发布时生成不可变版本号和哈希，回滚只切换当前发布指针。
- 审计写入与业务事务同库同事务，Trace ID 由请求过滤器生成并通过 `X-Trace-Id` 返回。
- 所有新增接口沿用 `/api/v1`、`ApiResponse<T>`、JWT 角色和现有错误格式。

## 非目标

本阶段不接入真实医院 HIS、支付、处方、消息队列、分布式锁、生产级对象存储，也不把离线评估结果包装成临床准确率。

## 验收标准

- 候补加入、offer、接受、过期和并发库存路径有单元/控制器测试。
- 医生完成预约必须同时创建摘要；患者越权读取返回 403。
- 文档重复上传返回已有版本；发布和回滚保留历史版本，管理员外访问返回 403。
- 写操作响应包含 `X-Trace-Id`，审计记录不含认证秘密。
- 默认 Maven 测试、Web 构建、小程序构建和发布脚本静态契约全部通过。
- Docker Compose 与 CI 文件只提供可复现入口，不在本地自动启动服务或修改远程资源。
